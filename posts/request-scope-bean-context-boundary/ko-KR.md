> 이 글에서 RequestScopeBean은 Spring의 @RequestScope를 적용한 요청 스코프 컨텍스트 Bean을 뜻한다.

요청 하나를 처리하는 동안 여러 계층에서 공통 요청 정보가 필요할 때가 있다. 예를 들어 요청 식별자, 호출 애플리케이션, 국가 코드, 라우팅용 사이트 코드처럼 HTTP 요청에서 시작하지만 비즈니스 DTO 자체의 의미와는 조금 다른 값들이다.

이때 흔히 세 가지 선택지가 생긴다.

1. 필요한 값을 메서드 파라미터로 계속 전달한다.
2. 요청 DTO나 공통 BaseRequest에 값을 끼워 넣는다.
3. Spring의 RequestScopeBean에 보관하고 필요한 컴포넌트가 주입받는다.

RequestScopeBean은 두 번째 방식의 DTO 오염과 첫 번째 방식의 긴 파라미터 릴레이를 동시에 줄여주는 것처럼 보인다. 문제는 이 편의성이 너무 좋다는 데 있다. 경계를 정하지 않으면 요청 단위 전역 변수처럼 변한다.

이 글의 결론은 단순하다.

> RequestScopeBean은 요청 단위 인프라 컨텍스트를 소수의 경계 컴포넌트가 공유할 때는 유용하지만, 비즈니스 로직의 입력값을 숨기거나 어디서든 꺼내 쓰는 저장소가 되는 순간 피해야 한다.

## 먼저 구분해야 할 것: 비즈니스 입력과 요청 컨텍스트

가장 먼저 봐야 할 것은 값의 출처가 아니라 의미다.

countryCode가 HTTP 헤더에서 왔다고 해서 무조건 RequestScopeBean에 넣어야 하는 것은 아니다. 주문 가격 정책이 국가에 따라 달라지고 해당 값이 유스케이스의 결과를 바꾼다면, 그 값은 사실상 비즈니스 입력이다. 메서드 시그니처나 명시적인 command/context에 드러나는 편이 낫다.

반대로 requestId처럼 로깅, 추적, 외부 호출 상관관계에만 사용되고 중간 서비스 계층은 그 값을 전혀 해석하지 않는다면 성격이 다르다. 이런 값은 요청 단위 인프라 컨텍스트에 가깝다.

판단 기준은 "어디서 왔는가"보다 "누가 의미를 이해해야 하는가"다.

## 파라미터 릴레이가 항상 나쁜 것은 아니다

다음과 같은 호출 흐름을 생각해보자.

~~~text
Controller
  -> Application Service
      -> Domain Service
          -> External Provider
~~~

최하단 Provider에서만 siteCode가 필요하지만 위의 세 계층은 값을 사용하지 않는다면, 모든 메서드에 siteCode를 추가하는 것은 단순 전달을 위한 시그니처 오염이 될 수 있다.

하지만 "파라미터가 많다"는 이유만으로 RequestScopeBean으로 옮기면 안 된다.

명시적 파라미터에는 중요한 장점이 있다.

- 호출자가 무엇을 제공해야 하는지 드러난다.
- 테스트가 숨은 컨텍스트에 의존하지 않는다.
- 비즈니스 로직의 입력이 정적 구조에 남는다.
- 비동기 경계나 다른 실행 컨텍스트로 넘어갈 때 손실 여부를 명확히 판단할 수 있다.

즉, 파라미터 릴레이의 비용과 명시성의 이점을 같이 봐야 한다.

## DTO에 요청 컨텍스트를 넣는 방식의 문제

다른 유혹은 요청 DTO 자체에 서버 내부 값을 넣는 것이다.

예를 들어 외부 클라이언트가 보내지 않은 requestId, 인증 결과, 내부 라우팅 값 등을 BaseRequest에 추가한 뒤 필터나 Advice에서 채워 넣을 수 있다.

처음에는 편하다. 이미 모든 서비스가 DTO를 전달하고 있기 때문이다.

하지만 시간이 지나면 DTO가 두 역할을 동시에 갖게 된다.

- 클라이언트가 보낸 입력
- 서버가 요청 처리 중 계산하거나 주입한 내부 컨텍스트

그러면 코드만 보고 값의 출처를 알기 어려워진다. 검증 시점도 흐려지고, 직렬화 대상인지 내부 전용인지 경계도 모호해진다.

DTO는 가능한 한 외부 계약 또는 유스케이스 입력이라는 본래 역할을 유지하는 편이 낫다.

## RequestScopeBean이 잘 맞는 경우

RequestScopeBean을 고려할 만한 조건은 다음과 같다.

~~~text
1. 값이 정확히 하나의 요청에 종속된다.
2. 중간 계층은 그 값을 사용하지 않고 단순 전달만 한다.
3. 실제 사용 지점이 소수의 인프라성 컴포넌트에 제한된다.
4. 비즈니스 유스케이스의 핵심 입력값이 아니다.
5. DTO에 넣으면 외부 입력과 내부 컨텍스트의 경계가 섞인다.
~~~

예를 들어 다음 정도는 비교적 자연스럽다.

- 요청 초입의 Filter 또는 Interceptor에서 컨텍스트 초기화
- 외부 연동 URL을 결정하는 Resolver
- 추적 정보를 외부 시스템에 전달하는 Provider
- 공통 로깅이나 correlation 처리를 담당하는 경계 컴포넌트

핵심은 "사용 지점이 적고 역할이 명확하다"는 것이다.

## RequestScopeBean이 위험해지는 순간

다음 징후가 보이면 사실상 요청 단위 Service Locator 또는 전역 상태로 변하고 있다고 봐야 한다.

- 일반 Service가 직접 주입받는다.
- Mapper가 컨텍스트를 조회한다.
- Validator가 숨은 요청 상태에 의존한다.
- Repository가 요청 컨텍스트를 읽는다.
- 대부분의 외부 Client가 같은 Bean을 직접 조회한다.
- 새 파라미터를 추가하기 귀찮을 때마다 Bean에 필드를 늘린다.

이 구조에서는 메서드 시그니처만 봐서는 실제 입력 의존성을 알 수 없다.

~~~java
public Result execute(Command command) {
    // 겉으로는 command만 필요해 보이지만
    // 실제로는 request-scoped state에도 의존한다.
}
~~~

테스트 역시 요청 스코프를 구성해야 하고, 비동기 처리나 스레드 전환이 생기면 수명주기 문제가 추가된다.

편의성을 얻는 대신 의존성의 가시성을 잃는 셈이다.

## 직접 주입 범위를 좁혀라

RequestScopeBean을 쓴다면 가장 중요한 규칙은 "누가 직접 주입받을 수 있는가"다.

예를 들어 다음 정도로 제한할 수 있다.

~~~text
직접 주입 허용
- 요청 초입에서 값을 설정하는 Filter / Interceptor
- 실제 값을 소비하는 Provider / Resolver 한두 곳

직접 주입 비허용
- 일반 Service
- Mapper
- Validator
- Repository
- 대부분의 Client
~~~

이렇게 하면 RequestScopeBean은 전역 저장소가 아니라 경계 사이의 짧은 연결 통로로 남는다.

또한 요청 초입에서 모든 값을 무조건 채우기보다, 책임이 분명한 값만 초기화하는 편이 좋다. 컨텍스트 객체가 계속 비대해진다면 구조가 다시 무너지고 있다는 신호다.

## 명시적인 context record가 더 나은 경우

RequestScopeBean 없이도 파라미터 폭발을 줄일 수 있다.

관련 값이 하나의 처리 파이프라인에서 함께 움직이고, 그 흐름 자체가 코드에 드러나야 한다면 명시적인 context record가 더 적합하다.

~~~java
public record RoutingContext(
        String appId,
        String countryCode,
        String siteCode,
        String requestId
) {
}
~~~

이 방식은 몇 가지 장점이 있다.

- 의존성이 메서드 시그니처에 남는다.
- 테스트가 일반 객체 생성만으로 가능하다.
- 요청 스코프 밖으로 이동해도 의미가 유지된다.
- 어떤 값들이 하나의 처리 문맥을 이루는지 명확하다.

반대로 중간 계층이 이 객체를 계속 받아서 그대로 다음 계층으로 넘기기만 한다면 RequestScopeBean을 다시 검토할 수 있다.

결국 두 방식은 경쟁 관계라기보다 가시성과 전달 비용 사이의 선택이다.

## 실무 판단 규칙

다음 질문으로 정리할 수 있다.

~~~text
이 값이 비즈니스 결과를 바꾸는가?
→ 그렇다면 명시적인 입력으로 둔다.

중간 계층이 값을 실제로 사용하는가?
→ 그렇다면 명시적인 파라미터나 context가 낫다.

중간 계층은 전혀 모르고, 요청 경계의 소수 컴포넌트만 사용하는가?
→ RequestScopeBean을 검토할 수 있다.

"파라미터 넘기기 귀찮다"가 가장 큰 이유인가?
→ RequestScopeBean을 쓰지 않는다.

직접 주입 지점이 계속 늘어나는가?
→ 이미 경계를 넘고 있을 가능성이 높다.
~~~

## 결론

RequestScopeBean 자체가 나쁜 구조는 아니다. 요청과 수명주기가 정확히 맞고, DTO에 내부 상태를 섞지 않으면서 불필요한 파라미터 릴레이를 줄일 수 있다.

하지만 그 장점은 사용 범위를 좁혔을 때만 유지된다.

가장 중요한 기준은 다음 한 문장으로 정리할 수 있다.

> 요청 단위 인프라 컨텍스트는 숨길 수 있지만, 비즈니스 로직의 입력 의존성까지 숨겨서는 안 된다.

RequestScopeBean을 도입할 때는 "쓸 것인가"보다 "어디까지 쓰게 허용할 것인가"를 먼저 결정하는 편이 안전하다.
